# 契约骨架编程（Skeleton-by-Contract）

> 状态：**设计提案**（阶段 0 之前）。本文不描述已实现的能力；凡标注"已有"的，
> 都能在 Code-agent 现有代码里找到；凡标注"新增"的，都还没写。
>
> 面向读者：决定要不要做这件事的人，以及阶段 0 的实验执行者。

---

## 0. 一句话与它的赌注

**人只维护三样东西——形状、义务、拓扑；实现（函数体）降级为可再生的派生物。**

- 形状（shape）：签名、类型、数据结构、可见性
- 义务（obligation）：不变量、失败模式、边界、复杂度/依赖预算
- 拓扑（topology）：谁用谁、先后顺序、失败如何传播

这个想法真正要赌的不是"AI 能写实现"（那是现成的），而是：

> **当实现可以被反复丢弃和重生成时，编程这件事剩下的部分是什么。**

推论很硬：**判据就是全部**。人越不写实现，"怎么证明这个身子是对的"就越成为唯一的承重墙。
所以本文所有机制都在服务同一件事：让"对不对"变成机器可查的事实，而不是人的信心。

**这个名字是占位符**（`Skeleton-by-Contract`），核心概念是"契约领着骨架长肉"。

## 1. 颗粒度与职责边界

### 1.1 谁写什么

| 颗粒度 | **人写**（AI 不可悄悄改） | **AI 写**（可再生） | **机器判** |
|---|---|---|---|
| 模块 / 包 | 边界、依赖方向、允许谁依赖谁 | — | 架构规则（已有：`codeintel/architecture.py`） |
| 类 | 身份、字段、不变量、生命周期、可见性 | 方法体 | 类型检查 + 不变量断言 |
| **函数** | 签名、义务、错误模式、复杂度/依赖预算 | **语句** | 证据（单测 / 属性 / 断言 / 静态检查） |
| 变量 / 常量 | 名字与语义、单位、取值范围 | 取值来源与推导 | 类型 + 断言 |
| **边（调用 / 依赖）** | 拓扑：先后、扇入扇出、失败怎么传 | — | 影响面（已有：`codeintel/impact.py`） |

### 1.2 两条定义级判断

**判断一：变量/函数/类只是节点，"设计"的主战场在边上。**
一个函数该不该存在、谁调用谁、出错时谁兜——这些决定系统好坏，而它们全是边。
因此本文把最低颗粒度定为 **「一个符号 + 它的至少一条边」**，而不是孤立的函数。

**判断二：复用的是义务与证据的模式，不是语句。**
"人不写实现，实现经验不就丢了？"——不丢，但它沉淀成"同类问题的义务长什么样、配什么证据、
历史上踩过什么坑"，而不是一段可以直接抄的代码。这是这个范式能够积累、而不是每次从零猜的前提。

## 2. 五个核心机制

| 机制 | 是什么 | 为什么不能省 | 现有可复用 |
|---|---|---|---|
| **M1 契约真源** | 签名/义务/拓扑是一等产物；实现文件里的签名必须与它逐字一致，不一致即拒绝 | 只要契约允许"写在注释里"，它一定先漂移，然后变成谎话 | `codeintel/spec.py`（行为卡片 + 断言数）、`purpose.py`（"自身契约"）、`store.py`（符号索引）、`graph.py` |
| **M2 骨架生成** | 人写契约 → 机器生成"签名 + `NotImplementedError` + 义务注释 + 证据骨架" → **人审骨架** | 审骨架比审代码便宜十倍；这一步就是"人做设计"的落点 | `scanner.py` / `parsers/*`（已有符号与结构） |
| **M3 义务账本** | 每个义务一个稳定 id（`OBL-xxx`）；每个实现体声明它满足哪些义务；**证据挂在义务上，不挂在文件上** | 实现可重写的前提是证据不随之丢失 | `patches.py`（改动台账）、`provenance.py`（溯源）、`decisions.py`（决策线程） |
| **M4 判定门禁** | 义务接进已有**有序验收清单**：判据多一档 `obligation:OBL-xxx`，门禁只报**第一个未满足**义务 + 进度 ρ | 没有门禁，"AI 说做完了"就是唯一判据 | `sessions/acceptance.py`（人工检查清单）与工具执行日志；自动证据门禁仍需新增 |
| **M5 漂移审计** | 定期出"契约 ↔ 实现"一致性报告：无实现的义务 / 无义务的实现 / 被改过的契约 | 漂移不会报错，它只会悄悄发生 | `codeintel/export.py`、`impact.py` |

### 2.1 义务与证据的形状（示意，非代码）

| 项 | 内容 |
|---|---|
| 义务 id | `OBL-0142`（稳定，永不复用） |
| 挂在哪个符号 | `routing.classify(prompt: str) -> Route` |
| 义务条文 | 空字符串输入必须返回默认路由；不得抛异常 |
| 证据 | `tests/test_task_routing.py::test_classify_picks_the_more_specific_task_type` |
| 约束 | 纯函数；不得读文件/环境；单次调用 O(关键词条数) |
| 谁声明 | 人（阶段 0 由人写在契约文件里） |
| 谁实现 | AI（只改函数体） |

## 3. 规则怎么制定

### 3.1 三条元规则（比任何具体条文都重要）

1. **规则必须写在契约里，不能写在文档里**——文档不会拦住任何一次提交。
2. **规则必须机器可查**——人盯、AI 自觉都不算规则，只算愿望。
3. **违反必须有后果**——拒绝执行 / 退回人工 / 记进决策线程。没有后果的规则会被迅速绕开。

### 3.2 规则表

| # | 规则 | 谁守 | 违反后果 | 机器怎么查 |
|---|---|---|---|---|
| R1 | 实现文件里的签名必须与契约**逐字一致** | 机器 | 拒绝提交 | 索引比对（`spec.py` + `store.py`） |
| R2 | **冻结清单**：AI 只能改函数体，禁止改签名/类型/可见性/异常契约 | AI + 机器 | 判为"契约变更"，必须人工批准 | `patches.py` + 写权限闸门 |
| R3 | 每个实现体必须声明它满足的义务；无主的实现 = 未授权代码 | AI | 门禁拒收 | M3 义务账本 |
| R4 | 每个义务必须有**可判定**的证据；无证据的义务 = 未验收 | 人 + AI | 不计入完成度 | M4 证据运行器 |
| R5 | 一次实现只动被指派义务涉及的文件 / 函数 | AI | 记 `outside_plan` 并退回 | `tasks.py` 的 `plan_scope_ok` / `outside_plan`（已有） |
| R6 | **不许改测试 / 证据来让自己通过** | AI | 直接判负 | 证据文件写权限 + diff 检查 |
| R7 | **不许改契约来让自己通过** | AI | 拒绝 + 记决策线程 | 契约文件对 AI **只读**（工具层强制） |
| R8 | 同一种失败连续 N 次 → 熔断交回人 | 机器 | 停止本任务 | `agent/breaker.py`（已有） |
| R9 | 未声明的假设必须**问人**，不许自己补 | AI | 记一次违规 | `ask_user_question`（已有）+ 收口自查 |
| R10 | 契约必须能生成"人看的沙盘"，否则等于没写 | 人 | 契约不合规 | `graph.build_digest` / 地图（已有） |

**R7 是命门**：只要 AI 能动契约，它就会用"改契约"的方式让自己通过——这和"改测试凑通过"是同一个病。
Janus Labs 的 `BHV-001`（测试作弊检测）量的正是这一类行为，说明这不是假想的风险。

## 4. 落到现有项目上

| 新概念 | 直接复用 | 需要新增 |
|---|---|---|
| 契约条目（签名 + 义务 + 证据） | `spec.py` / `purpose.py` / `store.py` / `graph.py` | 契约库 + 义务 id 空间 |
| 骨架生成 | `scanner.py` / `parsers/*` / `graph.py` | 生成器（契约 → 骨架文件） |
| 义务 → 任务 | `tasks.py`（plan/subtasks/**verify 命令**）、`parallel.py`（lanes/leases）、worktree 隔离 | 义务 ↔ 任务映射 |
| 判定 | `acceptance.py`（供人工检查的有序判据 + ρ） | `obligation:` 判据类型 + 证据运行器 |
| 只读契约 | `permissions/policy.py` 的策略表思路、工具启停（M21） | "契约文件禁止写入"闸门 |
| 人的介入 | `ask_user_question`（M31，阻塞式追问） | "未声明假设必须问"的提示词规则 |
| 可视化 | `MindMap.vue` / `NodeDetail.vue` / `PatchPanel.vue` / `TaskPanel.vue` | **契约角标**（有契约/无契约、义务数、证据覆盖率）+ 义务视图；diff 默认折叠成"满足了哪个义务" |
| 回退 | `checkpoints.py` / `rewind.py`（M29） | 契约快照作为回退锚（实现是派生物，不必回退） |
| 评测 | `scripts/janus_eval.py` 的思路 | 内部指标：契约满足率；外部指标：Janus 的行为轴 |

**一句总结**：这个项目已经具备约 80% 的基础设施——地图（形状）、spec/purpose（义务雏形）、
patches（证据台账）、验收清单（人工检查）、worktree（隔离）、地图 UI（显性）。
真正缺的只有一件事：**把"契约"从注释里请出来，变成一等公民与唯一真源。**

## 5. 怎么证明它比"人直接写代码"更好

### 5.1 指标

| 指标 | 含义 | 期望方向 |
|---|---|---|
| 人写行数 / 总行数 | 人的注意力花在哪 | ↓ 显著 |
| 契约变更率 | 人写的东西稳不稳 | 低，且每次都有理由 |
| 证据覆盖率（有证据的义务占比） | 这范式的地基 | ↑ 逼近 100% |
| 一次通过率 / 返工轮次 | AI 填体的效率 | ↑ / ↓ |
| **契约改后重生成正确率** | **"实现可丢弃"是否成立**（最重要） | ↑ |
| 回归率 | 重生成引入的破坏 | ↓ |

### 5.2 对照实验

固定一小批自包含任务（Janus Labs 那类题目正合适，见 `scripts/janus_eval.py` 的适配思路）：
A 组人直接写代码，B 组人写契约 + AI 填体，比 5.1 的六个指标。

### 5.3 **不适用清单**（必须同时写下，否则范式会被误用然后被骂）

探索性代码（连要什么都不知道）、性能/并发敏感的核心循环、一次性脚本、
强交互 / UI 手感类需求、契约无法判定的业务合规。

这些地方人直接写更快。**这范式换来的是"结构稳定 + 证据不丢 + 可无痛重写"，
代价是"单次实现往往不如老手手写的最优解"。** 长期演进的系统划算，短平快交付不划算。

## 6. 风险与反例

| # | 风险 | 为什么会发生 | 缓解 |
|---|---|---|---|
| 1 | **契约完备性悖论** | 不写实现就没人能保证契约够全；契约不够 → AI 补自己的假设 → 语义漂移 | 义务必须可判定（R4）+ 未声明假设必须问人（R9）+ 收口自查 |
| 2 | **不可判定性是硬边界** | 性能、并发安全、"这符合业务吗"不可判定 | 这类必须人给"约束或参考实现"，不许假装能判 |
| 3 | **AI 把契约当橡皮**（R7） | 改契约是最省事的"通过"方式 | 契约文件对 AI 只读；契约变更走人工 + 决策线程 |
| 4 | **人的认知负担可能更高** | 写契约比写代码更抽象 | **不要让人从零写**：先用 `spec.py`/`purpose.py` 从已有代码反向提取草案，人做"改"而不是"写" |
| 5 | **实现质量整体略降** | 派生物不如手写最优 | 用证据覆盖率与回归率兜底；关键路径允许"人写实现 + 冻结签名"的例外（见阶段 4 的待拍板项） |

## 7. 分阶段路线

| 阶段 | 做什么 | 成功判据 |
|---|---|---|
| **0（最重要，不写代码）** | 手工跑一遍范式（清单见 `contract-first-phase0-checklist.md`）：人只写"签名 + 义务 + 拓扑"，AI 填体，用**现有工具**判定 | 能回答两个未知：**人愿不愿意这样写**、**契约够不够** |
| 1 | 反向提取契约草案（复用 `spec.py`/`purpose.py`）→ 人审 | 一个已有模块的草案人只改了几处 |
| 2 | 地图上区分"契约层（人写）"与"实现层（可再生）" | 打开地图就能看出哪些是人的决定、哪些是机器的活 |
| 3 | 骨架生成 + `obligation:` 判据接进验收清单 | 门禁能拦住"无主实现"和"无证据义务" |
| 4 | 义务并行实现（复用 lanes/leases/worktree） | 一个模块多条义务并行，互不撞车 |
| 5 | 漂移审计报告 + 指标看板 | 每次契约变更都能看到影响面与证据覆盖变化 |

**为什么阶段 0 优先**：这件事最大的未知不是工程（底子够了），而是**人写契约的手感**。
先花一周用现有工具手工验证，比先写解析器理性——万一契约写不住，代码就白写了。

## 8. 待拍板（范式定义级，不是实现细节）

| # | 决策点 | 我的倾向 | 影响 |
|---|---|---|---|
| D1 | 契约放哪：同文件（注解 + docstring + 装饰器）还是独立产物/目录 | **先同文件**：复用现成工具链、AI 天然会写、人不用学新语法；跑顺再考虑独立 DSL | 决定阶段 1 的全部工作量 |
| D2 | 语言边界：先 Python-only 还是第一天多语言 | Python-only 做样板 | 决定解析器与证据运行器的复杂度 |
| D3 | 证据的最低档位：单测够吗，还是必须属性测试/类型检查/不变量 | 单测 + 类型检查为底，属性测试用于"边界类"义务 | 决定 R4 能否落地 |
| D4 | 人写实现的例外口：遗留代码与性能敏感处怎么办 | "冻结签名 + 反向提取契约"渐进纳管，不重写 | 决定与存量代码的关系 |
| D5 | 是否接受"边也是一等公民" | **必须接受**（见 §1.2 判断一） | 不接受就退化成"接口优先 + AI 填体"，价值小很多 |

## 9. 阶段 0 实测修正（已执行，详见 `contract-first-phase0-report.md`）

阶段 0 用**现有能力**手工跑完了（2 个模块、4 次独立实现、未写任何产品代码）。
实测推翻了本文几处假设，先记在这里，避免后来者按旧版理解动手：

| 本文原假设 | 实测结论 |
|---|---|
| §5.1「契约改后重生成正确率」是最重要指标 | **该指标饱和**：4 个独立实现全部一次通过，区分不出好坏。换成两个更硬的：**契约缺口数**（实现者标出的歧义条数）+ **分歧探测数**（同契约不同实现的行为差异数） |
| §6 风险 1「契约不完备 → AI 补假设 → 语义漂移」 | 成立，但**形态不同**：漂移不表现为实现分歧，而是"**一致地猜错**"+ 文案级漂移。三个实现在 14 个未定义边界上行为**完全一致**——所以"实现不一致"不是主要风险，**"缺口不被任何闸门发现"才是** |
| §2 M3「证据挂在义务上」 | 证实（9 条证据在 3 个完全不同的实现上一条未改）。但补一条硬要求：**证据必须断言"输出本身"**，不能只断言存在性/包含性——实测里 16/25 的渲染文案漂移就是只断言包含性漏掉的 |
| §2 M2「骨架生成」 | 证实必要，且暴露出实现要求：骨架必须是**冻结文件**，实现者不许写回原文件；"人决定的数据"（如关键词表）属于契约、要原样落地；配套需要一个**形状闸门**（比对公开符号/签名/dataclass 字段/import，不比函数体） |
| §3 R6/R7（不许改测试/契约） | 4 次实现**零违例**（形状闸门 + 证据哈希双重验证）。但仍必须做——这次没违例是因为 prompt 里明确禁止了，而 prompt 不是闸门 |

**一条方法论收获**：让实现者交出"**你这几条义务里哪几条只能靠猜**"的清单，
能把未来的实现分歧**提前变成可复核的契约条目**——实测里唯一的两个行为分歧点，
实现者在动手前就用文字预告了。所以这份清单纯交付物，且必须有人读；
但"要求如实报告"只是 prompt 约定，**规则仍须机器可查**。

## 附：名词表（先统一语言，后面才不会各说各话）
| 名词 | 定义 |
|---|---|
| **形状（shape）** | 签名、类型、字段、可见性、数据结构——"长什么样" |
| **义务（obligation）** | 必须成立的性质：不变量、失败模式、边界、预算——"必须做到什么" |
| **证据（evidence）** | 机器可执行的证明：单测、属性测试、类型检查、断言——"凭什么说做到了" |
| **拓扑（topology）** | 符号之间的边：调用、依赖、顺序、失败传播 |
| **骨架（skeleton）** | 由契约生成的空体结构：签名 + 义务注释 + 证据骨架 + `NotImplementedError` |
| **实现体（body）** | 函数内部的语句——**本文档的核心主张：它是派生物** |
| **契约变更（contract change）** | 对形状/义务/拓扑的任何改动。与"改实现"是两类改动，审批路径不同 |
| **漂移（drift）** | 契约与实现、或证据与义务之间的不一致，静默发生、不报错 |
| **违例（violation）** | AI 试图改契约 / 改证据 / 越界改动文件的行为记录 |
