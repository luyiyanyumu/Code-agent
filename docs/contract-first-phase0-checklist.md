# 阶段 0 手工实验清单（契约骨架编程）

> 目的：**在写任何代码之前**回答两个未知——①人愿不愿意这样写？②契约够不够？
>
> 时限：实验 A 与实验 B 各 **60–90 分钟**，同一个下午做完。
> 铁律：**全程不使用任何新功能**，只用 Code-agent 现有能力（地图 / `acceptance_set` /
> `todo_write` / `ask_user_question` / patch 台账 / checkpoints 回退 / pytest）。
>
> 设计文档：`docs/contract-first-design.md`

---

## 0. 准备（10 分钟）

- [ ] **不要在主线仓库里做实验**。复制一份或用 worktree：
      `git -C E:\CH-agent worktree add E:\csp-phase0 HEAD`（或直接 `robocopy` 一份）
- [ ] 起一个隔离实例（别用你正在用的 8765）：`set CODE_AGENT_HOME=E:\csp-phase0\home`
- [ ] 建一个实验目录：`E:\csp-phase0\`，里面放
      `exp-a\`（新模块）、`exp-b\`（已有模块重生成）、`PHASE0-CONTRACT.md`（契约载体）
- [ ] 准备一张秒表/计时器：**人写契约的时间**与 **AI 填体的时间**要分开记
- [ ] 打印或另开一页放"记录表"（§4），边做边填，**不要事后回忆**

**关于"契约载体"**：阶段 0 没有契约层，用 `PHASE0-CONTRACT.md` 手写；把里面的义务
**同时**用 `acceptance_set` 声明一遍——这样"义务"当场就变成门禁判据（这是现有功能对
契约层的最小模拟）。义务 id 暂用 label 文本（如 `OBL1-空输入返回默认路由`）。

## 1. 实验 A：新模块（测"人写的契约够不够"）

**选一个真实、小、可判定的需求**，不要用玩具题。推荐：
> 把会话事件流聚合成"本轮统计"的纯模块（轮数 / 工具数 / 耗时 / token）——
> 前端现在是在 `ChatView.vue` 里现算的，把它下沉成后端纯函数是有意义的真实需求。

### 步骤

- [ ] **A1** 人只写这些（**不许写函数体、不许写伪代码**）：
  - 形状：文件名、导出的类/函数名、参数与返回类型
  - 义务：至少 5 条，每条都要**能判定**（例：空事件流 → 全 0；不读盘不联网；
    单次遍历；同一输入两次调用结果相同；未知事件类型被忽略而不是抛错）
  - 拓扑：谁调用它（哪个模块）、它在什么顺序里被调用
- [ ] **A2** 把这 5 条义务用 `acceptance_set` 声明成有序清单（判据用
      `tool:` / `patch:` / `file_contains:` / `no_failures`）
- [ ] **A3** 让 AI **先生成骨架**：只有签名 + 义务注释 + `raise NotImplementedError` + 证据骨架。
      然后**人审骨架**（这一步是"人做设计"的落点）。
      记：「审骨架改了几处」——改得越多说明契约写得越不准。
- [ ] **A4** 让 AI 填实现。**过程中不要口头补充设计**；它若提问（`ask_user_question`），
      记录问题，如实回答；它若默默补了假设，记进"悄悄补的假设"表。
- [ ] **A5** 跑 pytest + `acceptance_check`。首轮不通过就返工，**记轮次**。
- [ ] **A6** 让 AI **重生成一次**（同样的契约，从头再填一遍体，丢掉上一版），
      看既有证据是否仍然全绿。→ **这是本实验最重要的一步**（"实现可丢弃"的最小验证）

### 实验 A 的关键观察

- [ ] AI 有没有试图改签名/类型？（R2 违例）
- [ ] AI 有没有试图改测试来通过？（R6 违例）
- [ ] AI 有没有在契约之外自己发明行为？（悄悄补的假设）
- [ ] 5 条义务里，有几条是 AI **事后**才让你发现"你忘了写"的？（漏义务数）

## 2. 实验 B：已有模块重生成（测"人改契约的手感"）

**对象**：`code_agent/agent/routing.py`（约 150 行，纯函数 + 一个小 dataclass，
已有测试 `tests/test_task_routing.py`，5 个用例）。

> 注意：`routing.py` 有 `ROUTES` 这类**数据**。数据算"形状"还是"实现"？
> 这正是实验要逼出来的判断——记录你的决定与理由。

### 步骤

- [ ] **B1** **反向提取**契约草案（不要从零写）：读现有代码 + 现有测试，
      在 `PHASE0-CONTRACT.md` 里写出形状 / 义务 / 拓扑。
      约定：**不许搬代码**，每条义务必须写成"必须成立的性质"而不是"它现在这么做的"。
- [ ] **B2** 人审草案，只改需要改的地方。记：「改了几处」「有没有发现现有实现与测试不一致」
- [ ] **B3** 让 AI **按契约重写全部函数体**（签名与义务一字不动）。
      **指定它必须先读契约、且不许读旧实现**（先把它挪走或改名）——否则它会照抄。
- [ ] **B4** 跑 `tests/test_task_routing.py`。全绿 = 契约抓住了行为；有红 = 契约漏了义务。
      把每个红灯翻译成"漏掉的那条义务"，补进契约再重生成一次。
- [ ] **B5** 记录 **契约改后重生成正确率**（第几轮全绿）——这是设计文档 §5.1 里最重要的指标。

### 实验 B 的关键观察

- [ ] 从代码反推契约时，你写出的是"性质"还是"描述现状"？（后者等于没写契约）
- [ ] 有没有哪条义务**不可判定**（只能靠"我知道它是对的"）？那一条就是不可契约的部分
- [ ] 重生成后行为一致、但实现更差/更好？（记录：这不是失败，是范式的代价/收益）
- [ ] 有没有哪条义务压根不该存在（现有实现里有、但没有任何证据支持）？

## 3. 停止规则（什么时候判定"手感不成立"）

| 现象 | 判定 | 动作 |
|---|---|---|
| 契约在 3 轮内仍被频繁修订（>50% 的义务改过） | **手感未成立** | 停止工程投入；先改契约表达方式（D1 决策） |
| AI 悄悄补的假设 > 每条义务 1 条 | 契约条文太松 | 把该条义务写成可判定的形式再试一次 |
| 人写契约时间 > 直接写实现时间 | 记录触发条件（哪类代码不适合） | 补进设计文档 §5.3 不适用清单 |
| 重生成后证据反复无法全绿（≥3 轮） | 证据太弱或义务相互冲突 | 检查证据质量，而不是怪 AI |
| AI 出现 R6/R7 违例 | **这是最重要的发现**，不是意外 | 记录现场（prompt + diff），它决定 R6/R7 的闸门必须在阶段 3 之前就做 |

## 6. 做完之后先别写代码

无论结果好坏，**下一步都不是写契约解析器**，而是：

- [ ] 如果手感成立 → 拿着实验报告去定 D1–D5，然后才进阶段 1
- [ ] 如果手感不成立 → 先改"契约怎么写"（表达方式），再重做本清单
- [ ] 无论哪种 → 把实验 A 的"重生成"步骤从一次提高到三次，看结果是否稳定
      （一次全绿可能是运气；三连全绿才叫"实现可丢弃"）
