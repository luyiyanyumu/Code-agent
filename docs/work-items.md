# 项目任务

代码页右侧的“任务”是项目工作的统一入口。“并行”作为执行方式提供，不再占用一个独立标签。

## 执行方式

- **团队执行**：需求成为 Lead 管理的子任务，执行智能体可以继续拆分子任务。适合日常修改，遵守当前项目的执行权限。
- **隔离执行**：在独立 Git 分支和工作目录中规划、执行，批准计划后开始修改，审查并合并后进入主干。
- **隔离并行**：多个隔离任务按文件范围和依赖执行。同一文件的后续任务等待前序合并，再从最新代码开始；结果按计划顺序合并，冲突时中止当前合并。

三种方式均接入同一个项目团队调度，受项目并发限制约束。批次的执行数设置仅用于进一步限制该批次，并不能增加项目总容量。Lead 协调工作，执行智能体保留递归派工、审批、预算和结果回执机制。

预算按执行者及其递归子任务链计算。处于同一次 Lead 执行中的子任务可以继承该链预算；从任务面板独立启动的多个车道各自建立执行链，批次本身没有额外的汇总 Token 上限。

## 状态与审查

执行完成、Lead 验收通过、代码已合并分别显示。取消、失败或预算耗尽不自动进入成功审查。列表显示实际执行阶段、权限申请、最近验证结果和错误；权限申请跳到产生申请的智能体会话处理。

任务的工作树或其中任何子智能体仍在排队、运行或等待审批时，不能合并、放弃或移除工作树。审查和验证也需要任务树空闲。代码变化后，已有验证需要重新执行。

## API 和历史任务

- `GET /api/v1/code/projects/{project_id}/work-items` 聚合团队工作、隔离任务、并行批次。不会执行任务、创建工作流成员或迁移历史会话。批次车道与所属任务的主执行智能体不重复作为顶层任务展示，递归子任务仍可追踪。
- `POST /api/v1/code/projects/{project_id}/work-items` 接受 `requirement`、可选 `title` 和 `execution_mode`（`team`、`isolated`、`parallel`）。隔离方式支持 `plan_first`、显式 `git_init` 和手动 `plan`。
- 现有任务、批次的计划、审查、验证、合并、放弃接口继续兼容，供统一任务详情使用。

历史隔离任务会话在下一次空闲派工时安全绑定到 Lead 团队，保留会话历史。正在执行的旧会话不会迁移或中断。统一列表仅返回结果摘要，完整证据保留在会话和执行记录中。
